# 개발 진행 방식

개발해야되는 크기를 작게 쪼개야 하기 때문에 TDD 방식으로 진행한다.

## docs 폴더 구성

| 파일 | 설명 |
| --- | --- |
| `PRD.md` | 제품 요구사항: "무엇을" 만드는가 |
| `TRD.md` | 기술 요구사항: "어떻게" 만드는가 |
| `REQUIREMENT.md` | 상세 요구사항: FR+NFR+US 통합 명세 |
| `API_SPEC.md` | API 엔드포인트 명세 |
| `DATA_MODEL.md` | DB 스키마, ERD, 비즈니스 규칙 |
| `COMPONENT_SPEC.md` | 컴포넌트 계층, Props, 이벤트 흐름 |
| `TEST_CASE.md` | TDD용 테스트 케이스 정의 |

위 문서들을 바탕으로 TDD 방식으로 개발을 시작한다.

## TEST_CASE.md — TDD의 시작점

구조는 다음과 같다.

**예시: 로그인 기능 TEST_CASE.md**

```
- TC-API-001: 올바른 아이디/비밀번호로 로그인 시 200과 토큰을 반환한다. (정상)
- TC-API-002: 존재하지 않는 아이디로 로그인 시 401을 반환한다. (예외)
- TC-COMP-001: 로그인 버튼 클릭 시 로딩 스피너가 표시된다.
- TC-COMP-002: 비밀번호 필드가 비어 있으면 제출 버튼이 비활성화된다.
- TC-INT-001: 로그인 성공 후 대시보드 페이지로 리다이렉트된다.
```

- **API 테스트**
  - API 테스트 케이스는 정상 케이스 + 예외 케이스로 구성한다.
- **컴포넌트 테스트**
  - 컴포넌트 테스트는 사용자 관점에서 작성한다. 내부 구현이 아니라 '사용자가 보는 것'과 '사용자가 하는 행동'에 초점을 맞춘다.
- **통합 테스트**

추적 매트릭스를 테스트 케이스 표와 함께 연결하여 각 테스트 케이스와 관련된 요구사항을 매핑하여 이 기능이 실제로 테스트 되고 있는가를 추적하게 한다.

**예시: 추적 매트릭스**

| 요구사항 ID | 요구사항 설명 | 테스트 케이스 ID | 상태 |
| --- | --- | --- | --- |
| FR-01 | 사용자는 아이디/비밀번호로 로그인할 수 있다 | TC-API-001, TC-COMP-001 | ✅ 통과 |
| FR-02 | 잘못된 로그인 정보는 에러 메시지를 표시한다 | TC-API-002, TC-COMP-002 | ✅ 통과 |
| FR-03 | 로그인 성공 시 대시보드로 이동한다 | TC-INT-001 | 🔲 미착수 |

## TDD 개발 흐름

문서 체계가 갖춰지고 나서 실제 개발을 시작할 차례이다.

기본적인 파일 및 폴더만 생성한다.

그 후 TDD는 3단계의 흐름을 반복하여 개발을 진행한다.

**RED (실패하는 테스트 작성) → GREEN (테스트를 통과하는 최소 구현) → Refactor (코드 개선, 테스트는 유지) → 다시 처음 반복**

각 사이클은 5~10분 이내로 짧게 가져가는 것이 원칙이다.
AI는 한번에 많은 코드를 생성하려는 경향이 있기 때문에 개발자가 의도적으로 사이클을 짧게 가져가도록 의식해야한다.

여기에 명세 확인하는 절차와 테스트 실행하는 절차를 추가하면 전체 TDD 개발 사이클은 다음과 같다.

1. **명세 확인** → API_SPEC.md + TEST_CASE.md 교차 확인
2. **Red** → 테스트 작성 (구현 코드 없음)
3. **테스트 실행** → RED는 실패하는 테스트 코드를 작성하는 것이기 때문에 전부 실패해야 된다.
4. **GREEN** → 테스트 최소 구현
5. **테스트 실행** → 테스트 통과 확인
6. **Refactor** → 코드 개선 (테스트 통과 유지)
7. **테스트 실행** → 테스트 통과 재확인
8. **다음 기능으로** → step 1로 돌아감
